# 为面试准备的C++知识页面——所谓八股

## 0，NULL，nullptr
* 在C中，NULL被定义为空指针，#define NULL  ((void*)0)
* 在C++中，NULL被定义为0，#define NULL 0，nullptr被定义为空指针
* nullptr可以避免函数重载的二义性

## void*指针类型
* void* 是一个指针，指向一块没有数据类型的内存
* 可以指向任何类型的地址，必须强制转换才能正常取值
* C中可以隐式转换，C++中不可以隐式转换

## int, unsigned int, long long, float, double类型
* int: 4，-2^31, 2^31 - 1
* unsigned int: 4, 0, 2^32 - 1
* long: 8，跨平台有问题
* float: 4
* double: 8
* int转换为float可能存在精度丢失：float前8位是指数，后23位是尾数，还有1位是符号位，因此当int绝对值大于2的24次方时，会丢失精度
* C++11之后，不要使用原生int/long，使用int32_t uint32_t int64_t, uint64_t

## 如何比较两个浮点数
* 绝对不能直接用 == 来比较浮点数的根本原因：IEEE 754 标准导致的浮点数精度丢失问题
* 绝对误差比较：只要差值的绝对值小于 epsilon，就认为它们相等
* 相对误差比较：我们需要根据数值本身的大小，动态放大或缩小我们的容差边界

## 指针的大小
* 指针本身存放的是内存地址，而内存地址的长度是固定的（与计算操作系统有关，32位或64位），32位系统中是4个字节，64位系统中是8个字节。

## 原码，反码，补码
* 正数的原码、反码、补码都相同
* 原码：最高位（最左位）表示符号位，0表示正数，1表示负数
* 负数的反码：除了符号位不变，其他位置逐位取反
* 负数的补码：在反码的基础上加1。对补码在做一次补码就可以得到原码

## 位运算
* 运算均在补码上进行
* &：位与，只有两个都是 1，结果才是 1。只要有一个 0 就是 0，常用：清零、奇偶、提取标志位
* |：位或，只要有一个 1，结果就是 1。两个都是 0 才是 0
* ^：位异或，相同为 0，不同为 1
* ~：取反，1变0，0变1
* <<：左移，左移若干位，高位丢弃，低位补0，相当于乘以2
* `>>`：右移，右移若干位，低位丢弃，正数高位补0，负数高位补1，相当于除以2
** 位运算，必须、强制将变量洗白为无符号类型
* bitset: 一个长度为N的二进制序列，可以和string和integer相互转换
* bitset<8> bitset1(12);  // 将12保存为8位二进制的序列
* bitset<8> bitset2("10101"); // 将字符串"10101"保存为8位二进制的序列

## RAII
* 资源获取即初始化，在构造函数中申请分配资源，在析构函数中释放资源，通过局部对象的生存期控制资源的生命周期。
* 在构造函数中初始化。局部对象在函数栈中声明后，会自动调用构造函数进行初始化。函数栈结束后，局部变量自动析构销毁，无需人工。常用于锁、智能指针、计时器等。

## 内存对齐
* 内存对齐是按照成员声明顺序依次安排内存的。
* 内存对齐的规则：（1）第一个成员相对首地址的偏移量为0，后面每一个成员相对首地址的偏移量为成员大小的整数倍；（2）最后整个结构体的大小为最大数据成员大小的整数倍。
* 内存对齐的好处：可以提高代码在不同平台的可移植性和内存访问性能。
    * CPU访问内存是按照内存读取粒度一块一块访问的
    * 不是所有硬件平台都可以访问任意地址上的数据

## 静态联编和动态联编
* 什么是联编：通过函数调用找到特定的函数代码块执行。通俗来说就是根据函数名（和参数列表）执行对应的函数代码块
* 静态联编：在编译期间进行的联编。优点是效率更高。编译器对非虚函数使用静态联编。
* 动态联编：编译期无法确定要执行的函数，在程序运行时选择正确的函数。编译器对虚函数使用动态联编。


## 向上强制转换和向下强制转换
* 向上强制转换：将派生类引用或指针转换为基类引用或指针，不需要显式类型转换。
```
因此，指向基类的指针或引用可以指向派生类的对象。
Male male;
Human* human = &male;
Human& human = male;
因此，在函数形参为基类的指针或引用时，实参可以为基类对象、派生类对象
```

* 向下强制转换：将基类引用或指针转换为派生类引用或指针，需要显式类型转换。
```
Human human;
Male *male = static_cast<Male*>(human);

Male* male = dynamic_cast<Male*>(human);  // 前提：Human 类里必须至少有一个 virtual 虚函数（为了拥有 RTTI 运行时类型信息）。
```

## 虚函数的工作原理
* 虚函数：是实现C++三大特性之一（多态性）的方法，提高代码复用性和接口规范化
* 虚函数表（V-table）：一片连续的内存，实际上是一个函数地址的数组。
* 如何实现：（1）在声明一个包含虚函数的类对象时，该对象中加了一个隐式成员，该成员为虚表指针，指向虚函数表。（2）调用虚函数时，程序将访问虚表指针，找到对应的虚函数表，然后根据使用的是第几个虚函数，调用虚函数表中对应顺序的函数。

## 虚函数的注意事项
* 构造函数不能是虚函数：构造函数是创造对象时自动调用的，不可能通过父类指针或引用来调用；从V-table角度来看，对象创建之前没有V-table，无法调用虚函数
* 如果一个类有子类，那么析构函数需要为虚函数：通过基类指针删除派生类对象时，如果基类析构函数不是虚函数，其行为是未定义行为
* 友元函数不能是虚函数。因为友元函数不是类的成员，只有成员函数才能是虚函数。
* 派生类中没有重新定义：使用基类版本或者派生链中最新版本。
* 重新定义将隐藏：在派生类中写了一个名字叫 func 的函数，不管它的参数是什么、是不是虚函数，它都会无差别地隐藏基类中所有名字也叫 func 的函数
    * 还想继续使用基类里其他参数版本的同名函数，你必须在派生类中显式地用 using 关键字把它“拉”下来：**using Base::func**;
    * 返回类型协变：正常情况下，如果派生类要 **Override** 基类的虚函数，要求“**函数名、参数列表、返回类型**”必须这三者完全一样
        * 唯一的例外就是**协变**：如果基类虚函数返回的是基类的**指针或引用**，那么派生类重写该函数时，可以把返回类型“缩小”为派生类的**指针或引用**
    * 如果基类中声明的虚函数被重载了，而在派生类中只重写了其中一个，根据“名称隐藏”规则，其他重载版本会被隐藏导致无法调用。
        * 解决方案有两个： 1. 在派生类中显式使用 using BaseClass::funcName; 暴露所有重载版本（推荐做法）；
                        2. 在派生类中重新接力定义所有的重载版本并透传调用。

## 纯虚函数
* 在基类中没有具体实现的函数体的虚函数，被称为纯虚函数，又称为接口
* 纯虚函数要求派生类必须对该函数提供具体实现，所有纯虚函数都有具体实现，类才能被实例

## C++11 现代指针哲学：左右值、移动语义与完美转发
* **值类别的底层定义与辨识技巧**
    * **左值 (Lvalue)**：能够用取地址符 `&` 拿到物理内存地址，**有独立名字**，表达式结束后依然存活的持久对象。
    * **右值 (Rvalue [prvalue + xvalue])**：代码中的字面量（如 `2`, `true`，除字符串外），函数的匿名返回值。它们**没有名字，无法用 `&` 取地址**，在所在行的分号 `;` 处立即死去。
    * **【极速判断法则】**：不管什么神仙类型，只要在代码里“有名字”，它那一刻的物理表现绝对就是左值！
* **【惊天谎言】`std::move` 根本不发生任何移动**
    * **本质**：`std::move` 在底层是零开销的，它仅仅在编译期执行了无条件的强制转型 `static_cast<T&&>(lvalue)`。
    * **作用**：强行剥夺一个左值的左值属性，让编译器把它当成“即将死亡的右值（将亡值）”来看待。
    * **真正效用**：对象内存在物理上的转移（如打断原指针、剥夺资源管理权），**100% 依赖于目标对象自身是否实现了高效的「移动构造函数 (Move Constructor)」**。如果没有，`std::move` 的强制转型也仅会降级触发传统的拷贝构造。
* **右值引用的“背叛”行为**
    * 因为“有名字的就是左值”这个铁律，当你写出 `void set(std::string&& str)` 时，虽然 `str` 绑定了一个右值，但 **`str` 这个变量本身在函数作用域内是一个实打实的左值！**
    * 如果在函数体内想把它继续传给别的右值接口，必须强行再次扒皮：`pass_on(std::move(str))`。
* **万能引用 (Forwarding Reference) 的严苛触发条件**
    * **规则**：形式为 `T&&`。当且仅当传入参数能促使 `T` 发生**实时的模板类型推导**时，它才是一把能随传入值形态而变化的“万能钥匙”。如果是推导过的类模板方法（如 `vector<T>::push_back(T&&)`），则无推导发生，它是纯粹的右值引用。
    * **引用折叠矩阵**：万能引用底层依赖于折叠规则，除了遇见“右值 + 右值”保留右值引用 (`&& && -> &&`) 外，只要沾染了哪怕一个左值引用 `&`，无论怎么折叠都会全部塌缩成极度安全的左值引用 `&`。
* **`std::forward` 与完美转发 (Perfect Forwarding)**
    * **痛点**：由于前面的“背叛”规则，所有作为参数传进来的右值，只要有了名字形参，在这个函数体内就变成了左值。这会导致嵌套调用时丢失原来的右值属性。
    * **救世主**：`std::forward<T>(param)` 是配套万能引用使用的条件转换器。它借助前面留存的 `T` 的模板推导记录，如果是原来是右值就原封转右值，是左值就原封转左值。保证参数在层层函数调用栈流转中，完全保住其最初始的值类别尊严。


## 万能引用
* 万能引用：函数既能接受左值类型的参数，也能接受右值类型的参数。
```
template<typename T>
returnType Function(T&& param) {
    Function2(param); // 函数内部对形参的直接使用，都是按照左值进行的。因此param是个左值类型
}
使用T&&类型的形参既能绑定右值，又能绑定左值
只有发生类型推导的时候，T&&才表示万能引用；否则，表示右值引用。
```

## std::forward
* 实现完美转发：std::forward会将输入的参数“原封不动”地传递到下一个函数中去。左值还是左值，右值还是右值。
* 步骤：（1）在模版中使用&&接受参数；（2）使用std::forward将参数转发给被调用的函数。
```
template<typename T>
returnType Function1(T&& param) {      // 万能引用：param既可以是左值类型，也可以是右值类型
    Function2(std::forward<T>(param)); // 完美转发：std::forward将param“原封不动“转发给 Function2
}
```

## placement new
* 常规new一个对象，会先分配一个对应的内存空间，然后调用对象的构造函数构造一个对象。
* placement new：在new后面提供一个参数，作为new的地址，new会在给定的内存地址处构造对象。
```
int i = new int(10); // 常规new对象

new (&i) int(5); // placement new
```

## operator new/delete
* (T*)::operator new(size): 开辟一个大小为size的内存空间，地址的初始类型为void*，需强制转换为T*才可使用
* ::operator delete(ptr, size): 释放一个以ptr为首地址大小为size的内存空间
* 我的理解：所以new就是operator new + placement new?
```
int* ptr = (int*)::operator new(4);
```

## trivial destructor
* trivial destructor: 这个析构函数其实连个屁都不放，它干的活儿为 0 。STL直接释放内存
    没有自定义析构函数
    没有任何虚函数，也没有虚继承
    继承的所有父类，它们的析构函数也全都是 Trivial 的
    所有成员变量，它们的析构函数也必须统统都是 Trivial 的
* non-trivial destructor: 用户自定义了析构函数。如果申请了内存空间，一定要显式释放。STL逐个析构

## ++i和i++
```
// ++i的实现，返回一个引用
int& operator++() {
    *this += 1;
    return *this;
}

// i++的实现，返回一个对象
int opertator++(int) {
    int temp = *this;   // 产生一个临时对象temp，效率变低
    ++(*this);
    return temp;
}
```
* 将前置 ++i 形成肌肉记忆，替代一切 i++
* 现代编译器对于原生的 int，底层汇编汇编出来的代码，i++ 和 ++i 是 100% 绝对一模一样、一字不差的

## 指针和引用的区别
* 指针是一个变量，存储的是一个地址；引用只是原变量的别名
* 指针可以有多级，引用只能有一级
* 指针的声明和定义可以分开，引用在声明时必须初始化
* 指针可以重新指向其他变量，引用初始化后不可改变
* 指针作为参数传递时，实质上也是值传递，将实参（地址）的一个拷贝传递给形参，因此实参（地址）不会改变，实参指向的内容可以改变
* 语法上指针和引用都可以作为类的成员变量，实际上不要用引用
* 引用的底层，就是一个 T* const p (指针常量)

## 传递函数参数时，指针和引用的区别
* 指针传递：本质还是值传递，传递的是地址。函数对形参的任何操作都是作为局部变量进行的，不会影响实参变量的值
* 引用传递：传递的是实参的引用。函数对形参的任何操作都会影响实参变量的值

## new/delete和malloc/free的异同
* 相同点：都是用于动态分配和释放内存
* 不同点
    1. 前者是C++运算符，后者是C++标准库函数
    2. new会自动计算分配内存的大小，malloc需要手动计算
    3. new是类型安全的，malloc不是
    4. new = ::operator new(size) + 构造函数，delete = 析构函数 + ::operator delete(ptr, size)；malloc和free不会调用相关函数
    5. new封装了malloc，直接free只是释放了内存，没有析构对象
    6. 前者返回具体类型指针，后者返回void类型指针

## static
* 在类或结构体外使用static
    * 隐藏，变量或方法只在该cpp文件的翻译单元中可见
* 在类或结构体内使用static
    * 类或结构体中，静态属性是所有类实例共享的

* 在局部作用域内使用static
    * 生存期和作用域：静态局部变量的生存期延长为整个程序的生存期，但是作用域仍是局部

## const 与只读语义
* **核心本质 (防坑必考)**：
    * `const` 提供的是**编译期的语法检查**，防止程序员产生意外的写操作。
    * **全局/静态 const**：通常被放在 `.rodata`（只读数据段），由 OS 和 MMU 硬件限制写权限，强行写入会导致崩溃 (Segfault)。
    * **局部/栈上 const**：分配在栈中，**不受 MMU 保护**！内存页依然是可读写的。只是编译器阻止你修改，若通过 `const_cast` 强行修改栈上的 const，属于引发灾难的**未定义行为 (UB)**。
* **声明规范**：const 变量在声明时必须初始化（除非修饰的是具有默认构造函数的类对象）。
* **顶层和底层const**
    * **顶层 const**：const 作用于对象本身，指针本身不可变。
    * **底层 const**：const 作用于所指引的数据，指向的数据不可变。
* **类型推演口诀：从右向左读法则**
    * `const int* p;` -> `p` 是 pointer to int const（指针可以变，指向的 int 数值不可变）。
    * `int* const p;` -> `p` 是 const pointer to int（指针本身是 const 锁死的，但可以通过它修改 int 数值）。
## 现代 C++ 中 const 的进阶 (C++11+)
* **`constexpr` 才是真正常量**：`const` 只是意思是"只读"（可能在运行期通过函数返回值才确定）；如果需要一个在**编译期**就能确定的真常量（可用于数组大小声明、模板参数），必须使用 `constexpr`。
* **const 在类中的应用**：
    * **const 成员变量**：只能通过构造函数的成员初始化列表 (Initializer list) 赋初值。
    * **const 成员函数**：实质是将被隐式传递的 `this` 指针变成了 `const T* const` 类型。
    * **特例：`mutable` 破壁人**：如果在逻辑上被认为是“读操作”的 const 成员函数中，需要修改某些内部状态（如给 `std::mutex` 上锁，或更新 LRU Cache），则对应的成员变量必须声明为 `mutable` 才能绕过编译器的 const 拦截。
    * **只要一个成员函数在逻辑上不应该改变对象的状态，就必须、立刻、马上在后面加上 const**            

## 直接初始化 (Direct Initialization) 与 拷贝初始化 (Copy Initialization)

* **直接初始化**
    * **语法**：`T obj(args);` 或 C++11 统一初始化 `T obj{args};`
    * **底层机制**：直接将实参转交给匹配的构造函数（或重载解析出的最佳构造）。
    * **核心特权**：可以无视 `explicit` 关键字的阻拦，即使是被声明为 `explicit` 的构造函数，也能被直接初始化稳稳命中。
    
* **拷贝初始化**
    * **语法场景**：使用等号 `T obj = value;`、按值传递函数参数、函数按值返回。
    * **底层机制（经典）**：如果类型不匹配，编译器会先寻找一个**非 `explicit`** 的转换构造函数，用 `value` 生成一个**临时对象**，然后再调用该类的**拷贝构造函数（或移动构造函数）**来初始化 `obj`。
    * **权限限制**：拷贝初始化在其生命周期的任何隐式转换环节中，都**绝对无权调用被 `explicit` 标记的构造函数**。

* **【高频考点】C++17 的强制拷贝消除 (Guaranteed Copy Elision)**
    * 在 C++17 之前，写 `T obj = T(args);` 在语义上确实会调用一次拷贝/移动构造。
    * 但在 C++17 及其之后，标准**强制要求**编译器进行 RVO（返回值优化）级别的省略。此时如果等号右边是一个纯右值临时对象，编译器会**直接在 `obj` 的内存空间上原地构造**，彻底消除拷贝/移动的步骤。此时即便你的类删除了拷贝和移动构造函数（`= delete`），这段代码依旧能完美编译并以极致性能运行。


## 野指针和悬空指针
* 产生原因
    * 野指针：没有初始化的指针，指向对象已经消亡，指针空间释放后未置空
    * 悬空指针：指向的内存被释放掉的指针
* 解决办法
    * 野指针：使用引用，定义指针时及时初始化，释放后及时置空
    * 悬空指针：释放之后及时置空

## C和C++类型安全
* 类型安全：代码不会访问自己没有被授权的内存区域，很大程度上等价于内存安全
* C中的类型安全：C只在局部上下文中表现出类型安全
* C++中的类型安全：C++相比于C更具有类型安全性
    * new操作符返回的指针类型为具体对象指针，而不是void*
    * const关键字，dynamic_cast关键字设计类型检查
    * 模版支持类型检查

## 浅拷贝 (Shallow Copy) 与 深拷贝 (Deep Copy)
* **浅拷贝坑与本质**：
    * **机制**：编译器默认生成的拷贝行为，直接对对象内存进行逐字节的拷贝（Bitwise Copy）。如果对象内有指针，则只拷贝指针本身的 8 字节地址。
    * **致命灾难（Double Free，防坑必考）**：由于新旧对象的指针指向同一块堆内存，当这俩对象先后被销毁时，同一块堆区资源会被它们的析构函数 `delete` 两次，直接引发程序崩溃（核心已转储 / Segfault）。

* **深拷贝的实现规范**：
    * **机制**：如果带有堆区指针资源，我们必须打破默认拷贝，主动为新对象在堆区新 `new` 出一块同等大小的内存，并将旧内存里的**内容完全复制**过去。
    * **【高频核心】三/五法则 (Rule of Three/Five)**：如果是需要手动深拷贝的类，它必然自己管理着底层资源。因此，**析构函数、拷贝构造函数、拷贝赋值运算符（以及 C++11 引入的移动构造和移动赋值）**，这五员大将**必须同生共死，被全部手动重写**，不能只重写其中一个。

* **【架构师心法】现代 C++ 的零法则 (Rule of Zero)**
    * **最高境界是不写深拷贝**。工业界极度反感在业务代码中手动管理 `new/delete` 和重写深拷贝。
    * **解决方案**：只要把类中裸奔的 `T*` 指针，替换为具有自管理能力的 `std::vector`、`std::string` 或智能指针（`std::shared_ptr` 等），该类就可以直接享受完美无瑕的深拷贝语义，程序员即可实现**零代码内耗**（不用手动写任何析构和拷贝函数）。


## 内联函数 (`inline`)：从性能辅助到链接神器的演进
* **经典面孔（宏代码的上位替代）**：
    * **设计初衷**：为了取代 C 语言中危险的 `#define` 宏函数。`inline` 既能像宏一样在调用点展开（省去压栈出栈的函数调用开销），又能享受编译器严格的**参数类型检查**和**作用域安全**。
    * **类内隐式内联**：直接在类或结构体内部定义（也就是写了函数体实现）的成员函数，会被编译器**自动隐式当作内联函数**，无需手动加 `inline`。
* **【高频踩坑】内联只是“建议”而非“强制”**：
    * 编译器对内联拥有绝对裁决权。如果函数内包含循环、递归、体积庞大，哪怕加上了 `inline` 关键字，编译器也会残忍拒绝展开。反之，短小的函数即便没写 `inline`，在开启优化 (`-O2/-O3`) 时也会被编译器主动内联。
* **【架构师核心】现代 C++ 赋予的真正使命：绕过 ODR 原则**：
    * 在现代 C++ 工程中，`inline` 的核心价值在于**解决多重定义冲突（Multiple Definition Linker Error）**。
    * C++ 严禁在头文件 (`.h`) 中定义普通函数，否则被多个 `.cpp` 包含后会链接报错。若将其修饰为 `inline`，则是向链接器颁发了“去重特权”，允许它被全局多次包含，链接器最终会自动挑选一份保留。这是实现 Header-only 开源库（如大多数 Boost 库、C++ 模板代码）的底层基石。
    * **C++17 新增拓展**：引入了 `inline static` 机制，让静态成员变量也能享有相同的 ODR 豁免权，直接在类内完成初始化。


## 封装与继承的权限控制 (public / protected / private)
* **访问权限（类的封装契约）**
    * **public**：对外提供的接口契约，类的内外部均可访问。
    * **protected**：对外的黑盒，但对派生类开放的扩展接口。
    * **private**：绝对的内幕黑盒，仅类自身内部可见。*(架构红线：所有数据成员默认绝对 private，禁止图省事设为 protected，否则会彻底破坏类的封装性。)*

* **继承权限（类的衍生关系模式）**
    * **法则与推演：【天花板法则】**。指定的继承方式，就是基类成员在派生类中的**最高权限上限**。
        * `public` 继承：不压低上限。基类的 `public/protected` 在派生类中保持原样。
        * `protected` 继承：天花板为 `protected`。基类的 `public` 被强行降格为 `protected`。
        * `private` 继承：天花板为 `private`。基类所有可见成员全部被降格为 `private`。
        * *(注：基类的 `private` 永远对派生类隐藏，无法触及。)*
        
* **【高阶架构拷问】三种继承的真正工程意义**
    * **`public` 继承（唯一正统的继承）**：象征 **"Is-A" (是一个)** 的关系。完美遵循里氏替换原则 (LSP)，是 C++ 运行时多态（动态绑定）的绝对前提。
    * **`private / protected` 继承（隐藏的复用手段）**：象征 **"Implemented-in-terms-of" (根据...实现)** 关系。对外切断了一切“Is-A”的联系，多态能力失效。
    * **现代优先组合原则**：在实际工程中，极其不推荐使用 private 继承。优先使用**对象组合 (Composition)** 来代替 private 继承以实现代码复用；仅在需要重写基类虚函数、或者为了极致抠内存触发“空基类优化(EBCO)”时，才迫不得已使用 private 继承。


## 大小端与网络字节序 (Endianness)
* **概念定义（内存模型的基础）**：
    假设存储 32位整型 `0x11223344`（`11` 为最高有效字节 MSB，`44` 为最低有效字节 LSB）。
    * **大端序 (Big-Endian)**：高位字节存放在低地址。符合人类从左到右阅读习惯。
        * *内存增长方向 [低 -> 高]*：`11 22 33 44`
    * **小端序 (Little-Endian)**：低位字节存放在低地址。符合计算机 CPU 加法器底层从低位进位的处理逻辑。现代 x86 和大多数 ARM 服务器**均采用小端序**。
        * *内存增长方向 [低 -> 高]*：`44 33 22 11`
* 【业界绝对标准】：TCP/IP 协议栈强制规定，所有在网络上传输的多字节二进制整数，都必须统一使用“大端序（Big-Endian）”。因此，大端序也被统称为网络字节序；而你的机器原生使用的字节序（通常是小端），被称为主机字节序（Host Byte Order）。

`bool isLittleEndian() {
    union {
        uint16_t i;
        uint8_t c[2];
    } u;
    u.i = 0x0102;          // 赋值一个 2 字节整型
    return u.c[0] == 0x02; // 查看低地址字节（数组0下标处），如果是低位数据 0x02，就是小端
}

#include <bit>
if constexpr (std::endian::native == std::endian::little) {
    // 编译器会直接走到这里，因为绝大多数服务器（x86）都是小端
} else {
    // 对大端机器的特殊处理分支
}`

## volatile, mutable, explicit，extern关键字
* **volatile (防坑警告：与多线程无关！)**
    * **核心机制**：易变性指示符。强制编译器每次都直接从内存地址物理读写该变量，**绝对禁止**将其缓存在 CPU 寄存器中，也禁止将其与其他直接赋值语句合并优化。
    * **正确场景**：读写内存映射的硬件寄存器（MMIO），或操作中断/信号处理程序的标志位。
    * **【致命架构盲区】**：在现代 C++ 中，**一律禁止使用 `volatile` 来保证多线程安全！** 它既不能保证操作原子性，也无法建立内存屏障（无法阻止编译器/CPU的指令重排序）。多线程的数据同步必须使用 `std::atomic` 和 `std::mutex`。
* **mutable (打破常量的破壁人)**
    * **核心语义**：强制解除编译器对成员变量的 `const` 锁定。
    * **高阶用法**：当类的成员函数被声明为只读（`const` 函数）且对外承诺不改变对象状态时，如果你为了底层机制（如加行锁 `std::mutex`、更新缓存命中率等）不得不修改对应内部变量，则该内部变量必须被声明为 `mutable`，方可绕过编译器的只读拦截。
* **extern (链接期的红娘)**
    * **`extern` 变量声明**：用于跨翻译单元共享全局变量。在一个 `.cpp` 中定义，在其他 `.cpp` 中通过 `extern type var_name;` 声明，告诉链接器去别处寻找实体实现。
    * **`extern "C"` (防止名字粉碎 Name Mangling)**：C++ 编译器为了支持函数重载，会在编译期将函数名和参数类型混编成复杂的底层符号。使用 `extern "C"` 包裹函数，是强制 C++ 编译器“降维”使用 C 语言的纯文本命名规则导出符号，这是 **C/C++ 混合编程** 以及 **编写供跨语言调用的动态库 (.so/.dll)** 的唯一基石。
        * 限制：1. 包裹区内失去 C++ 函数重载能力；2. 跨语言公开接口的参数与返回值必须降级为 C 风格（裸指针、基本数据类型）；3. 头文件中必须配合 #ifdef __cplusplus 宏使用，否则纯 C 编译器包含该头文件时会报语法错误
* explicit：**关闭编译器在参数传递或拷贝初始化时“自作主张”的隐式类型转换行为，避免引发业务逻辑 Bug**
    **所有单参数构造函数都必须强制加上 `explicit`**

## C++ 内存分配宏观视角：三种 new 的形态与底层机制
* ** plain new (常规 new)**
    * **语法**：`T* p = new T(args);`
    * **机制**：底层调用 `operator new` 申请内存，随后调用 `T` 的构造函数。
    * **防坑必考**：分配内存失败时，**必然抛出 `std::bad_alloc` 异常，绝不返回空指针**。因此对 plain new 进行 `if (p == nullptr)` 的非空判断是毫无意义的废代码。
* ** nothrow new (不抛异常的 new)**
    * **语法**：`T* p = new(std::nothrow) T(args);`
    * **机制**：迎合 C 语言遗留下来的错误处理习惯。如果分配失败，它会吞下异常，**静默返回 `nullptr`**。适用于嵌入式等禁用了 C++ 异常机制（`-fno-exceptions`）的极端环境。
* **【高阶核心】placement new (定位 new)**
    * **语法**：`T* q = new(buffer) T(args);` (须包含头文件 `<new>`)
    * **核心机制**：**纯粹调用构造函数，完全不向操作系统请求分配内存**。它就在你传入的指针 `buffer` 所指的现成内存区域上，原地构造对象。
    * **架构场景**：这是实现高性能 **C++ 内存池 (Memory Pool)**、无锁环形队列 (Ring Buffer) 的唯一基石。用于彻底消灭高频 `new/delete` 带来的系统调用开销和内存碎片。
    * **析构的毁灭陷阱**：通过 placement new 构造的对象，生命周期结束时**绝对禁止对其使用 `delete`**（会引发系统崩溃）。必须**手写显式调用其析构函数**来清理资源：`q->~T();`。


## C++ 的异常处理 (Exception Handling) 现代规范
* **核心机制 (try / throw / catch)**
    * 先执行 `try` 块代码；若遇异常则用 `throw` 抛出对象，随后栈展开，由对应类型的 `catch` 块精准捕获。
    * **【工程铁律】**：**传值抛出，传常引用捕获** (`catch (const std::exception& e)`)。按引用捕获不仅能避免多余的拷贝开销，更核心的是能防止**对象切片 (Object Slicing)**，完美保留派生类异常的多态信息。
* **【时代眼泪与现代王权】异常声明规范**
    * **史前遗迹 (被彻底废弃)**：`void func() throw(int);` 这类动态异常规范在 C++11 被弃用，在 **C++17 中已被完全从标准中删除**，属于非法的编译错误。
    * **现代王者 `noexcept`**：现代 C++ 只有两极：默认可能抛出任何异常，或者声明为 `noexcept` 绝对不抛异常（`void func() noexcept;`）。
    * **`noexcept` 性能核武**：标注 `noexcept` 的函数能大幅减少编译器的栈展开辅助代码，极大提升性能。**强烈强制要求**：类的移动构造、移动赋值、析构函数必须标为 `noexcept`，否则 `std::vector` 等容器扩容时将退化为深拷贝，极其拖慢性能。
* **标准异常类体系 (`<stdexcept>`)**
    * 所有标准异常均继承自基类 `std::exception`，通过调用其虚函数 `e.what()` 可获取异常详细字符串。
    * `std::bad_alloc`：`new` 操作符动态分配内存失败时抛出。
    * `std::out_of_range`：`std::vector::at()` 或 `std::string::at()` 下标越界时抛出（注意：`operator[]` 越界通常直接 UB 不抛异常）。
    * `std::bad_cast`：`dynamic_cast` 强制将基类**引用**转换为非法的派生类引用时抛出。（注：转化指针失败仅返回 `nullptr`，不抛异常）。

## 类成员初始化：初始化列表 (Member Initializer List)
* **构造函数体内“赋值” (Assignment)**
    * **机制**：在执行函数体 `{ ... }` 的代码之前，对象的所有成员其实**已被默认构造完成**。在体内执行的所谓初始化，本质上是调用了 `operator=` 进行二次赋值。对于 `std::string` 等复杂对象，这会导致无意义的“先默认构造，后覆盖赋值”的双重性能浪费。
* **成员初始化列表 (Initialization)**
    * **机制**：在类的构造函数形参后以冒号 `:` 展开。这是真正的“在分配内存的同时原地直接构造对象”，一步到位，是 C++ 初始化类成员的性能最优解。
    * **【核心铁律】4 种强制必用场景**：遇到以下情况，**必须且只能**使用初始化列表，否则甚至无法通过编译：
        1. 成员是 `const` 常量。
        2. 成员是引用类型 (`&`)。
        3. 成员对象所在的类没有默认构造函数（必须显式传参）。
        4. 需要调用基类的非默认构造函数。 
* **【致命防坑】极其反直觉的初始化顺序**
    * **规则**：成员变量的真实初始化顺序，**100% 取决于它们在类定义（头文件）中的声明顺序**，而**完全无视**你在初始化列表中书写的顺序！
    * **规范**：如果变量之间互相依赖，极易因为声明顺序问题导致把未初始化的“垃圾内存”赋值给其他变量。因此，工业界强制要求：**初始化列表中的书写顺序，必须与类中的声明顺序绝对保持一致。**


## 面向对象的核心骨架：三大特性深度剖析
* **一、 封装 (Encapsulation)：安全与隔离的结界**
    * **浅层语法**：将数据（属性）和操作这些数据的方法（函数）捆绑成一个类，通过 `public/private` 划分可见性边界。
    * **深层架构意义 (数据隐藏)**：外界无法直接碰触底层数据，必须通过类提供的 `public` 接口进行交互。这不仅**保护了对象内部业务逻辑的一致性和合法性（防御性编程）**，更实现了**高内聚低耦合**——底层数据结构的修改，绝不会波及和弄瘫痪外部的调用侧代码。
* **二、 继承 (Inheritance)：复用与扩展的双刃剑**
    * **浅层语法**：派生类自动获取基类的非私有属性和方法，并在此基础上添加新特性。
    * **深层架构分类 (C++特色)**：
        * **接口继承 (public)**：表达绝对的 `Is-A` 关系，外界完全可以把子类当作父类来无缝使用。这是实现运行时多态的前提。
        * **实现继承 (private/protected)**：仅仅为了“白嫖”基类内部的底层代码（`Implemented-in-terms-of`）。但现代 C++ 极度反对滥用继承，**强烈倡导“组合优于继承”**，以打断层级过深的强耦合链条。
* **三、 多态 (Polymorphism)：“同一指令，万千化身”**
    * **核心真谛**：暴露统一的操作接口，但底层却由于目标对象的真实类型不同，而执行完全不同的行为逻辑。
    * **【高频必考】C++的两种多态面孔**：
        1. **动态多态 (运行时多态)**：基于 `public` 继承机制和 `virtual` **虚函数机制**。在运行时，通过向上转型（将派生类对象的地址赋给基类指针/引用），调用虚函数时依靠**查询动态的虚函数表（V-Table）**来进行迟绑定（Late Binding）。这也是经典 OOP 的精髓。
        2. **静态多态 (编译期多态)**：这是 C++ 的独门绝技！基于**函数重载**（同名不同参）和**模板泛型（Templates）**，在代码编译阶段，编译器就已经推导出了具体的类型并生成了确切的代码（早绑定 Early Binding），无需任何运行时查表开销（性能天花板）。


## C++ 四种核心类型转换 (Cast 机制解析)
* **【架构原则】为什么禁用 C 风格强转 `(T)val`？**
    * C 风格强转语义过于混沌（它会在底层盲目尝试各种转换直到成功），极不安全，且在百万级代码库中无法进行全局文本检索 (`grep`)。C++ 四大特有的 cast 故意设计得很长很难看，就是为了在做代码审查 (Code Review) 时提供绝对显眼的标记。
* **1. `static_cast` (常规与良性转换)**
    * **语境**：最通用的转换，告诉编译器“我知道可能会损失精度或发生隐式转换，请帮我静默处理”。无任何运行时开销。
    * **场景**：基础类型的安全转换（如 `double` 转 `int`）；普通类层次间的向上转型（子转父）；**最重要的**：用于将 `void*` 反向且安全地转回原本类型的指针（在回调函数中常用）。
* **2. `const_cast` (脱壳转换)**
    * **语境**：C++ 中唯一能合法去除（或添加）底层 `const` / `volatile` 属性的转换。
    * **【致命红线】**：用它去除 `const` 且修改数据，**仅在此数据最初始的时候被声明为非 const 时才是安全的**。强行去修改一个原生定义的常量，属于极其危险的 **未定义行为 (UB)**。
    * **场景**：给古老的无 `const` 设计的 C 语言遗留库 (Legacy API) 传参时迫不得已的妥协。
* **3. `reinterpret_cast` (底层的暴力美学)**
    * **语境**：让编译器关闭一切类型检查系统，强行对指针（或引用）背后的二进制比特流（内存块）换一种极其暴力的解释视角。甚至不产生额外的 CPU 指令。
    * **场景**：极端的底层操作。如网络大端小端收发包时的 `char*` 与 `Struct*` 互转，或者指针与足够长的整数类型 (`uintptr_t`) 之间的互相转换。
* **4. `dynamic_cast` (带有安全气囊的动态转)**
    * **语境**：依赖底层对象内部在运行时维护的 **RTTI (Run-Time Type Information)**，专用于在具有继承关系的类的多态环境（含有虚函数）中，进行安全的**向下转型 (Downcasting)**（父转子）。
    * **【性能盲区】**：运行时查表开销极其巨大。在追求极致低延迟的系统（游戏引擎内核、高频交易等）中，通常从编译器级直接禁用 RTTI 从而封杀该操作。
    * **【异常考点】**：如果转换的是**指针**，失败时温柔地返回 `nullptr`；如果转换的是**引用**，由于 C++ 不存在空引用的概念，失败时会残暴地直接**抛出 `std::bad_cast` 异常**。


## 内存管理核心：栈 (Stack) 与 堆 (Heap) 的底层架构
* **栈 (Stack) ：极致性能的工作台**
    * **归属与生命周期**：由操作系统为每个线程分配的**私有**内存区。变量的分配与释放由编译器自动隐式管理，函数执行完（弹栈）即销毁。
    * **底层机制与性能**：**性能天花板**。分配内存仅需一条硬件汇编指令（移动栈顶指针 `%rsp`）。内存地址通常**从高向低**生长。
    * **致命限制 (Stack Overflow)**：容量极小（Linux 默认 8MB，Windows 默认 1MB）。绝对禁止在栈上分配大数组或进行极深的递归，否则会导致栈空间耗尽，程序立刻被 OS 强制杀死。
* **堆 (Heap) ：广袤而危险的自由之海**
    * **归属与生命周期**：整个进程的所有线程**共享**的巨大内存区域。生命周期由程序员或内存分配器接管，若不显式释放，直到进程结束才会被 OS 回收。
    * **底层机制与性能**：**性能瓶颈**。申请内存（`new/malloc`）需要陷入复杂的内存分配算法（如 `ptmalloc`）去查表寻找空闲块；若容量不足还需触发昂贵的**系统调用 (`brk`/`mmap`)**。频繁分配易产生内存碎片。内存地址通常**从低向高**生长。
    * **现代 C++ 大厂规范 (RAII 与智能指针)**：
        * 极其排斥手写 `new/delete`。
        * **最高纲领**：必须使用**智能指针 (Smart Pointers)** 或 **STL 容器 (`std::vector` 等)**。利用栈对象生命周期结束时自动调用析构函数的物理特性，来**自动、确定性地释放**其所管理的堆内存资源，从根本上杜绝内存泄漏。



## 函数调用机制与栈帧 (Stack Frame) 的内核揭秘
* **核心基础设施 (x86-64汇编)**
    * **`rbp` (Base Pointer)**：栈底指针寄存器，固定指向当前函数栈帧的底部。
    * **`rsp` (Stack Pointer)**：栈顶指针寄存器，随着局部变量的增减动态上下浮动。
    * **`rip` (Instruction Pointer)**：指令指针寄存器，永远指向 CPU 下一条要执行的代码地址。
* **【高频核心】现代 64 位架构 (System V ABI) 的传参规范**
    * 为了极致性能，**前 6 个参数原则上不入栈**，直接通过 CPU 寄存器传递（顺序为：`rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`）。
    * 超过 6 个的参数才会进入内存堆栈，压栈顺序为 **从右向左**。
    * **返回值寄存器**：函数的返回值默认放在 `rax` 寄存器中带出给调用者。
* **C 语言标准栈帧的建立与摧毁全过程**
    1. **参数入栈**：调用者按**从右向左**的顺序将多余参数压入栈中。**（这种精妙的设计保证了参数个数可变函数如 `printf` 时，最左侧第一个确定参数与栈底指针的偏移量永远固定！）**
    2. **压入返回地址**：调用者执行 `call` 指令，硬件自动将原本紧跟在 call 后面的**下一条指令地址压栈**，然后将 `rip` 指向目标函数入口。
    3. **建立新栈帧 (Prologue)**：目标函数内部首先执行：
        - `push rbp` (将上一个函数的栈底地址备份入栈)
        - `mov rbp, rsp` (将当前栈顶作为自己全新栈帧的栈底)
    4. **局部变量空间**：通过 `sub rsp, N` 将栈顶继续向下延伸，挤出存储函数内局部变量的空间。
    5. **摧毁与返回 (Epilogue)**：函数执行完毕后，执行 `leave`（等价于 `mov rsp, rbp; pop rbp` 恢复旧栈帧），最后执行 `ret` 指令将当初压栈的返回地址弹给 `rip`，CPU 完美跳回最初位置继续执行。


## 静态类型，动态类型，静态绑定，动态绑定
* **静态类型 (Static Type)**：对象在代码声明时明确写出的类型，由编译器在**编译期**绝对确定。
* **动态类型 (Dynamic Type)**：指针或引用在程序的运行那一刻，物理内存中实际指向的对象的类型，在**运行期**决定。
* **静态绑定 (Early Binding)**：函数的调用地址或属性的访问，完全依赖于对象的**静态类型**。由编译器在编译时写死。普通函数、函数重载、模板都是静态绑定。
* **动态绑定 (Late Binding)**：函数的调用依赖于对象的**动态类型**。在运行时通过查表（如虚函数表 V-Table）决定地址。多态底层的重写 (`override`) 虚函数就是动态绑定。
* **【高阶防坑毒点】：绝不重定义虚函数的默认参数**
    * 虚函数的映射是**动态绑定**的（运行时随指针真实身份而动）。
    * 但是！虚函数缺省的**默认参数值却是静态绑定**的（编译期由指针的声明类型写死，为了保证执行性能）。
    * **灾难表现**：如果子类重写了父类虚函数的默认参数，当通过父类指针调用子类时，会出现**“执行的是子类的函数体，但压入的却是父类的各种默认参数值”**的诡异现象，引发极难排查的逻辑崩溃。

## 全局变量 vs 局部变量的底层剖析与架构红线
* **生存期 (Lifetime) 与 致命陷阱**
    * **局部变量**：生于本作用域 `{` 的入栈，死于作用域 `}` 的出栈（RAII 析构）。
    * **全局变量**：生于 `main()` 函数正式执行之前的加载期，死于程序退出。
    * **【致命盲区 SIOF】**：跨越不同 `.cpp` 文件的全局对象的初始化先后顺在 C++ 标准中是**完全未定义**的。这极易引发全局对象间的依赖崩溃（如对象 A 的构造函数依赖对象 B，但 B 还未被 OS 构造）。**大厂规避铁律**：用**局部静态变量 (Local Static)** 的首次调用延迟实例化，取代一切裸露在外部的全局对象依赖。
* **作用域 (Scope) 与 链接可见性**
    * **局部可见**：仅在声明它的代码块 `{}` 内部可见，外界完全隔离。
    * **全局/文件可见**：默认是外部链接（**External Linkage**），所有文件通过 `extern` 关键字均可染指；如果加上了 `static` 或放入匿名命名空间 `namespace {}`，则权限降级为内部链接（**Internal Linkage**），被严格隔离在被声明的 `.cpp` 墙内。
* **底层存储分配 (OS 模型)**
    * **堆栈区 (Stack)**：分配局部变量（含局部参数）。不仅读写极快，且在编译产生的目标文件（exe/elf）中**不占用任何二进制物理磁盘空间**。
    * **全局数据段 (Data Segment)**：
        * **`.data` 段 (已初始化)**：存放被显式赋了非 0 值的全局变量。这个初始值会被真实“烧录”并占据可执行二进制文件的物理体积。
        * **`.bss` 段 (未/零初始化)**：存放毫无初始值、或初值为 0 的全局变量。它们在可执行物理文件中**占据 0 字节体积**。程序在运行加载时，OS 会根据 BSS 表瞬间在内存中为它们虚空开辟对应容量的存储页并自动清零。 


## 指针算术 (Pointer Arithmetic) 与步长陷阱
* **加减运算的核心本质**
    * 指针加上或减去一个整数 `N`，其底层真实的内存地址移动量并不是 `N` 个字节，而是 **`N * sizeof(指针所指向的类型)`** 个字节。步长由目标类型严格定义。
* **【大厂考点 1】：`void*` 的运算禁区**
    * 严格 C/C++ 标准下，对 `void*` 进行加减运算**属于非法操作（直接编译报错）**，因为未知类型无法推导步长。
    * *跨平台陷阱*：GNU (GCC) 编译器有一个私有扩展，强行令 `sizeof(void) == 1`，但正规工程严禁依赖此特性。正确的做法是强制转型给 `char*` 或 `uint8_t*` 后再操作。
* **【大厂考点 2】：指针相减的物理意义**
    * 两个同类型指针可以相减（加法无意义），其结果**不是两者相距的核心字节数，而是相距的“元素个数”**。
    * 结果的规范数据类型为带有符号的 **`ptrdiff_t`**。
    * **红线前提**：相减的两个指针必须指向**同一块连续的数组内存空间**，否则运算属于未定义行为 (UB)。
* **【大厂考点 3】：高维指针（数组指针）的暴走步长**
    * 对于指向数组的指针，如 `int (*p)[10]`，执行 `p + 1` 会直接跨越一整行的物理内存（即步长为 `10 * 4 = 40` 个字节）。在解析音视频帧、图像矩阵的裸内存块时需极其警惕。


## 函数指针与现代 C++ 回调机制 (Callable Objects)
* **传统 C 风格函数指针 (底层本质)**
    * **语法**：`returnType (*func)(paramType);`
    * **本质**：代码指令在编译后存放在内存的代码段（Text Segment）。函数名本质上就是这段代码首地址的常量。函数指针保存了该地址，通过它可以实现函数的动态调用。
    * **底层架构应用**：是 C 语言实现泛型（如 `qsort` 的比较函数）、事件回调、以及 **C++ 底层虚表 (V-Table，本质是函数指针数组)** 实现动态多态的绝对核心基石。
* **【高频踩坑】类成员函数指针的降维打击**
    * **禁区**：类的**非静态成员函数**绝对不能直接赋值给普通的 C 风格函数指针！因为它们隐藏了强绑定的 `this` 指针参数，导致首地址签名不匹配。
    * **传统破局**：如果必须配合遗留的 C 语言回调 API（如 `pthread_create`），必须将类的回调函数声明为 `static` 静态函数（剥离 `this` 依赖）。
* **【现代大厂规范】C++11 的终极回调容器：`std::function`**
    * 在现代 C++ 工程中，我们使用 `std::function<returnType(paramType)>` 来彻底取代丑陋的 C 风格函数指针。
    * **降维级优势**：它是一个万能的“可调用对象 (Callable)”安全容器。无论是普通的 C 函数、还是仿函数 (Functor，重载了 `operator()`)，甚至是带捕获列表的 **Lambda 表达式**，统统都可以无缝塞进 `std::function` 中进行传递和调用。它是现代观察者模式 (Observer Pattern) 和异步任务库的灵魂。


## C++ 构建四大流程：从源代码到二进制可执行文件
1. **预处理 (Preprocessing)**
    * **核心**：暴力的文本替换（只操作物理文件纯文本）。
    * **动作**：展开所有 `#define` 宏定义；处理所有的条件编译指令（`#ifdef`、`#else`）；把 `#include` 包含的头文件内容直接“复制粘贴”插入到代码文件中。
    * *(工具：预处理器 cpp，产物 `.i` 文件)*
2. **编译 (Compilation)**
    * **核心**：语言的高维翻译与优化（绝不涉及目标链接）。
    * **动作**：对纯净的 C++ 代码进行词法、语法、语义分析，生成抽象语法树 (AST)。随后应用复杂的编译期优化算法（如函数内联、循环展开），将其翻译成底层的**汇编语言 (Assembly)**。
    * *(工具：编译器 gcc/clang，产物 `.s` 汇编文件)*
3. **汇编 (Assembly)**
    * **核心**：降维机器码。
    * **动作**：汇编器将汇编指令逐一翻译为 CPU 原生能执行的 0/1 机器码指令，生成**可重定位的目标文件 (Relocatable Object File)**。此时所有的文件都是独立的孤岛。
    * *(工具：汇编器 as，产物 `.o` / `.obj` 目标文件)*
4. **链接 (Linking) 【高频核心考点】**
    * **核心**：缝合孤岛，符号重定位。把所有 `.o` 文件和外部依赖库拼装成可执行文件。根据链接的库种类不同，分为两条路线：
    * **A. 静态链接 (Static Linking)**：链接器将目标所依赖的静态库（`.a` / `.lib`）中的二进制代码**完整拷贝并打包**进最终的可执行文件中。
        * **优点**：部署极其简单，生成的可执行文件独立运行，无需依赖外部系统环境的动态库版本。运行速度极快。
        * **缺点**：最终产生的文件体积庞大；多个相同程序的实例运行时会在物理内存中产生多份相同库代码的副本，极度浪费内存资源；第三方库每次更新都必须重新编译整个项目。
    * **B. 动态链接 (Dynamic Linking)**：链接器**不拷贝代码**，只在可执行文件中记录下符号跳转和依赖信息。直到程序**被 OS 真正运行起来时**，才由动态加载器去把动态库（`.so` / `.dll`）加载入内存并接通电路。
        * **优点**：可执行文件极小；真正的**物理内存共享**（多个进程依赖同一份底层 `.so` 时，物理内存只存一份副本）；库代码解耦，可支持热更新，只需替换 `.so` 文件而不必重新编译主程序。
        * **缺点**：可能引发致命的 **DLL 地狱 (依赖缺失或版本不匹配导致启动即崩溃)**；相比静态链接，程序在启动阶段有轻微的链接延迟性能损耗。


## 友元 (friend)：破坏封装的合法“后门”
* **友元函数 (必要之恶)**
    * **机制**：定义在类外的普通全局函数，但因类内部给予的 `friend` 声明，获得了访问该类底层 `private/protected` 成员的特权。
    * **【极高频考点】唯一强制场景**：重载输入/输出流操作符（`operator<<` 和 `operator>>`）。因左操作数必须是 `ostream/istream`，该重载函数必然是独立于类的全局函数，为读取私有数据，必须将其声明为内部类的友元。
* **友元类 (强耦合的架构红线)**
    * **机制**：若类 A 将类 B 声明为友元，则 B 中的所有成员函数均可无视访问权限，直接蹂躏 A 的私有数据。
    * **大厂代码规范**：业务逻辑中**极度反感**使用友元类，它彻底击碎了面向对象引以为傲的封装性和低耦合。
    * **合法豁免场景**：
        1. **紧密依存底层结构**（如 `Tree` 类将 `TreeNode` / `TreeIterator` 设为友元）。
        2. **白盒单元测试**（如生产类将 `GTest` 的测试用例类设为友元，以便从外部注入私有 mock 数据或窥探内部运行状态）。
* **友元关系的三大铁律 (特性)**
    1. **单向的**：A 把 B 当朋友（B 能看 A 的私有），不代表 B 把 A 当朋友（A 看不到 B 的私有）。
    2. **不可传递的**：B 是 A 的朋友，C 是 B 的朋友，C 绝对不是 A 的朋友。
    3. **不可继承的**：父类的朋友，默认无权探视子类的私有库房。


## 并发编程核心基石：各种锁的底层解剖
* **互斥锁 (Mutex)**
    * **机制**：一次仅允许一个线程进入临界区。拿不到锁的线程会被 OS 加入阻塞队列。
    * **底层代价**：引起高昂的**线程上下文切换 (Context Switch)** 开销。适用于持锁时间较长、包含复杂逻辑或 IO 操作的场景。
    * **【C++大厂规范】**：严禁手动调用 `lock()` 和 `unlock()` 以防忘记解锁导致死锁。必须使用 RAII 风格的智能锁守卫：`std::lock_guard` 或更灵活的 `std::unique_lock`。
* **自旋锁 (Spinlock)**
    * **机制**：拿不到锁时，线程不会休眠，而是在 CPU 上执行原地死循环（Busy-Wait）疯狂尝试。
    * **底层优势**：彻底免除了上下文切换的开销。极度适用于多核环境、且**临界区代码执行极快**（如只是修改几个变量立刻释放）的微秒级加锁场景。可通过 C++11 的 `std::atomic_flag::test_and_set` 轻松实现。
* **读写锁 (Read-Write Lock)**
    * **机制**：读共享，写独占（只允许一个写者操作，如果有写者，拒绝所有读者）。C++17 中引入为 `std::shared_mutex`。
    * **【高频踩坑】写饥饿问题**：在“读”极其密集的场景下，源源不断的读者涌入可能导致读锁一直处于未完全释放状态，从而使长期排队的写者被活活“饿死”。
* **条件变量 (Condition Variable)**
    * **【核心定位】**：互斥锁用来解决“互斥”问题，而**条件变量用来解决线程间的“同步（等待-通知）”问题**。当条件不满足时，线程自动解开互斥锁并进入睡眠；直到别的线程改变了条件并发出了 `notify` 信号将其唤醒。
    * **【致命红线】虚假唤醒 (Spurious Wakeup)**：由底层 OS 调度缺陷导致，睡眠的线程可能在无通知情况下诡异地自我唤醒。**防御守则：对条件变量的 `wait()` 判断，必须、且绝对只能放在 `while (条件不满足)` 循环中，绝不能用 `if`。**


## 引用的底层实现与内存假象
* **底层机制与假象（面试分水岭）**
    * **语法的假象**：在 C++ 语法层面上，引用仅仅是原变量的一个“别名 (Alias)”，对外不暴露自己的地址（对引用取地址 `&b`，取到的其实是被引用对象 `a` 的地址）。
    * **底层的真相**：在汇编语言的物理实现上，主流 C++ 编译器（GCC/Clang）会将不得不分配内存的引用，秘密转换成一个**“指针常量” (`T* const`)** 来处理（即内部保存了地址，且该地址终生不可更改，每次访问时由编译器偷偷帮你加上 `*` 进行解引用）。
* **【致命追问】引用到底占不占物理内存？**
    * 答案是：**看编译器的优化和使用场景**。
    * **占 0 字节（被完全优化）**：对于局部作用域内的简单引用，编译器会直接在编译期的符号表中将其与原变量绑定，映射到同一块内存或寄存器，此时引用**不占据任何额外的物理存储空间**。
    * **占指针大小（通常 8 字节）**：当引用作为**类的成员变量**，或是作为**未被内联的函数的形参**时，为了维持地址的物理传递，它会被降级为真实的指针，实打实地占据一块物理内存。
* **类内应用与惨痛代价**
    * C++ 允许使用引用作为类的成员变量。
    * **初始化铁律**：引用必须在出生就绑定目标，因此**只能且必须在类的构造函数的“初始化列表 (Initializer List)”中为其赋值**。
    * **架构代价**：一旦类中包含了引用成员，该类将被编译器没收默认的**拷贝赋值运算符 (`operator=`)**，变成一个“不可被等号随意赋值”的残疾类。若需保留可赋值特性，大厂规范要求使用 `<functional>` 中的 `std::reference_wrapper<T>` 替代裸引用成员。


## 编译器的底层盲区与翻译单元 (Translation Unit) 黑洞
* **什么是真正的翻译单元 (TU)?**
    * 并非单纯的 `.cpp` 文件，而是：**1 个 `.cpp` 源文件加上它所 `#include`（物理展开复制）的所有头文件头文件的庞大代码集合**。
    * **编译慢的元凶**：由于 `#include` 的物理复制特性，同一个头文件若被 N 个源文件包含，编译器将被迫对该头文件进行 N 次重复的词法/语法分析。
* **编译器的“信息隔离墙”原则**
    * 编译器在将一个 TU 编译为目标文件 (`.o` / `.obj`) 时，**绝对无法跨越边界去偷看其他 `.cpp` 文件的内容**。
    * 遇到只有声明没有定义的外部符号（函数/全局变量），编译器会盲目信任并在生成的目标文件中留下“重定位空洞”，把校验真实实现的黑锅完完全全地甩给**链接器 (Linker)**。
    * *工程排错指南*：语法错误 (`Syntax Error`) 归编译器管；符号找不到 (`Undefined Reference to...`) 归链接器管。
* **【现代 C++ 革命】跨越历史包袱的 C++20 Modules**
    * 为彻底根除 `#include` 翻译单元带来的编译速度灾难与重复定义 (ODR) 隐患，C++20 正式引入 **模块化 (Modules)**。
    * 抛弃预处理复制，改用 `import` / `export`。模块仅被编译器**解析和编译一次**并缓存为二进制模块接口集（如 `.pcm`），后续引入时直接读取 AST 结构文件，实现百万行代码的秒级增量编译，彻底根除“头文件循环依赖”。


## 模板 (Template)：C++ 的静态多态与泛型双刃剑
* **核心本质：代码的图纸 (Blueprint)**
    * 模板在被定义时**并不是真实的可执行代码**，它只是一台宏观的“代码生成器”。
    * **【高频考点】模板实例化 (Instantiation)**：只有在代码中真正被调用、并推导出具体类型（如 `List<int>`）的那一刻，编译器才会大笔一挥，以这套图纸为准，为你生成一份专属于 `int` 的真实 C++ 代码并进行编译。这种在编译期搞定类型的魔法，被称为**静态多态 (Static Polymorphism)**。
* **大厂避坑指南一：必须是 Header-Only (全在头文件)**
    * 传统 C++ 将声明和实现分离（分别放入 `.h` 和 `.cpp`）。但模板**绝不允许**分离！
    * **原因**：编译器在实例化模板时，必须瞬间在当前 `.cpp` (编译单元) 亲眼看到完整的函数体实现。若实现被隔离在其他的 `.cpp` 里，会导致编译器只画了皮肉而没有灵魂，最终在链接期爆发海量的 `Undefined Reference` 报错。
* **大厂避坑指南二：二进制大爆炸 (Code Bloat)**
    * 当在代码中调用了 10 种不同类型的该模板时，编译器会在底层物理生成 10 份完全独立的代码。滥用庞大的模板类极易导致最终编译产物体积呈指数级膨胀，拖慢启动速度并破坏 CPU 缓存。
* **【现代 C++ 革命】C++20 Concepts (概念)**
    * 传统模板对传入的类型缺乏约束，一旦传错，模板在内部展开失败，会爆出成百上千行犹如天书般的报错堆栈。
    * C++20 引入 `Concepts` 机制（如 `requires` 关键字），允许在模板定义时强制限定类型的语法契约（例如限定 `T` 必须实现了 `hash` 函数）。类型不符会在调用处直接被优雅地一击毙命，终结了长达三十年的模板报错地狱。


## 拷⻉构造函数：为什么必须是传引用？为什么必须加 const？
* **第一道铁律：为什么必须是引用传递（拒绝值传递）？**
    * **致命原因：防⽌⽆限递归导致栈溢出**。
    * **底层逻辑**：在 C++ 中，任何对象“按值传递 (Pass-by-value)”的底层本质，就是隐式地调用该类的拷贝构造函数来生成一个副本。如果拷贝构造函数本身也是值传递，就会陷入死循环：“为了调用拷贝构造 -> 必须先值传递复制参数 -> 为了复制参数 -> 必须再次调用拷贝构造...”，最终导致系统 Stack Overflow 崩溃。因此，编译器在语法层面强制规定其必须为引用传递。
* **第二道铁律 (大厂追问)：为什么必须是常引用 (`const T&`) 而不是普通引用 (`T&`)？**
    * **原因 1（业务逻辑的安全底线）**：拷贝操作在语义哲学上是“只读”的。在克隆一个对象时，我们绝对不期望（也不允许）在这个过程中意外修改或弄脏了“原版”对象的数据。`const` 锁死了这种可能性。
    * **原因 2（编译原理的硬性限制：绑定右值）**：这是一个极度高频的踩坑点！在 C++ 中，**非常量的普通引用 (`T&`) 是绝对不允许绑定到“临时对象 (右值 Rvalue)”上的**。
        * 假设你写了一行代码：`MyClass a = func_return_obj();`，函数返回的是一个转瞬即逝的匿名临时对象。如果你没有加 `const`，编译器会直接报错，拒绝用临时对象来初始化 `a`。
        * 而**常引用 (`const T&`)** 拥有一项特权：它可以安全地绑定到临时对象上，并合法地延长该临时对象的生命周期，直到拷贝动作完美结束。


## 正则表达式 (`<regex>`) 与性能黑名单
* **C++11 标准库的三大核心运作机制**
    1. **`std::regex_match` (完全匹配)**：要求整个目标字符串与模式绝对吻合，哪怕多一个空格也算失败。主要用于严格的整行格式验证（如校验邮箱格式）。
    2. **`std::regex_search` (部分搜索)**：在庞大的字符串中巡逻，只要发现任何满足正则约束的子串（Substring）就立即返回成功，并将匹配内容抓取至 `std::smatch` 结果集中。
    3. **`std::regex_replace` (查找并替换)**：在目标字符串中扫荡所有符合模式的子串，并统一替换成指定的新字符串。
* **【必备语法红线】：原生字符串字面量 (Raw String Literal)**
    * **痛点**：由于 C++ 会优先转义 `\` 符号，正规的正则 `\d+` 必须写出脑残反人类的 `\\d+`，极难维护。
    * **解法**：在业务逻辑中编写复杂的正则字符串时，强制大范围使用 C++11 的 **`R"(模式)"`** 语法。它能屏蔽 C++ 编译器的转义解析，实现“所见即所得”的极客体验。如：`std::regex r(R"(\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,7}\b)");`
* **【大厂底层排雷】：正则的性能陷阱与封杀名单**
    * **陷阱 1（频繁构造引发耗时黑洞）**：`std::regex` 对象的构造并不是简单的字符串赋值，而是要在底层极其昂贵地构建复杂的有限状态机 (Automata)。**绝对严禁**在频繁调用的循环体内部声明正则对象。高危代码应剥离，并统一加锁设为 `static const std::regex ...` 保证仅在程序启动时预热编译一次。
    * **陷阱 2（被大厂永久拉黑的标准库）**：由于 Linux GCC (GNU `libstdc++`) 早期对 `<regex>` 的底层实现存在严重缺陷，不仅匹配奇慢，还会遭遇极端耗时的**正则回溯攻击崩溃 (ReDoS)**。
    * **业界底牌**：在 Chromium、腾讯等极高并发的 C++ 基建中，标准库 `<regex>` 通常是被明令禁用的。取而代之的是工业界的王者：**Google RE2** 库，它从底层算法杜绝了回溯退化，保障了服务器哪怕面对恶意正则也能在线性时间内跑完。


## 函数返回值的底层路由与生命周期红线
* **原生类型的极速快递 (`rax` 寄存器)**
    * 若返回体积小（通常 <= 8 字节）的原生类型（如 `int`, `double`）或各种指针/引用。编译器根本不需要触碰主存，直接将结果塞进 CPU 的 **`rax` 回报寄存器**中带出，由调用方直接从 `rax` 提取，性能登顶。
* **【死亡红线】严禁返回局部变量的指针 / 引用**
    * 当函数执行完毕弹出栈帧 (`pop rbp`) 时，所有局部栈变量的生命周期被 OS 在逻辑上当场宣判死刑。
    * **【高频雷区】**：虽然出栈不仅是一条指针改变指令，不会消耗 CPU 周期去物理清空残骸内存（这导致了原本“按引用返回”取得的数据“有时看起来是正常的”这种错觉），但该堆栈区域已彻底沦为野区，随时会被中断响应或其他函数的下一层栈帧无情碾压覆写。此操作属于最恶劣的 **未定义行为 (UB)**，是野指针/悬空引用的万恶之源。
* **【现代标配】大方地按值返回复杂对象 (RVO / NRVO)**
    * **旧时代误区**：认为不能按值（`By Value`）返回一个非常庞大的局部堆栈对象（如包裹着几万个元素的 `std::vector` 对象），怕引发天价的整块内存拷贝。
    * **现代 C++ 魔法 (返回值优化 Return Value Optimization)**：自 C++17 起强制规定，当函数按值返回局部对象时，编译器会直接在底层将其解耦（偷偷将外部准备接收该对象的内存地址作为隐藏参数传给函数）。函数会**直接在调用方的栈帧中原地完美构造该对象**。
    * **结果**：做到了 **0 拷贝、0 移动**，性能开销和返回一个指针一样低！大厂规范极度鼓励这种兼具安全性与极限性能的防错写法。


## RTTI
* RTTI是什么： RTTI 使得 C++ 程序能够在运行时确定对象（通过基类指针或引用所指向的对象）的实际派生类型
* RTTI怎么用：编译器在构建包含虚函数的类时，会生成虚函数表 (vtable)。为了支持 RTTI，编译器通常会在 vtable 的开头（或某个固定偏移量处）插入一个隐藏的指针，该指针指向一个 std::type_info 对象，其中包含了该类的具体类型信息。
* 通过两个运算符来使用：dynamic_cast 和 typeid
* 好处
    * 类型安全：dynamic_cast 是受检查的转型，处理复杂多重继承 / 菱形继承：在处理拥有虚基类的复杂继承网络中的交叉转型（Cross-casting）时，只有 dynamic_cast 能够正确计算指针的偏移量
* 坏处
    * 性能开销极其昂贵：dynamic_cast 并不是简单的一条指令。为了验证类型，在复杂的继承体系中，它可能需要遍历继承树的元数据
    * 空间开销：开启 RTTI 会为每一个多态类生成额外的 type_info 结构；RTTI 必须存储整棵类继承树的拓扑结构；每个 vtable 都会增加一个指向对应 type_info 对象的指针，导致库比较大
